YappyNotes: the architecture

Four projects, dependencies running one way, and two mechanisms worth understanding before you change anything: how a keystroke becomes a single UPDATE, and why a running countdown never writes to disk at all.

A companion to docs/plan.md, which is the authority. This page adds the moving pictures; where the two disagree, the plan wins. Source: algorisys-oss/yappynotes. The figures step: use the buttons, or ← and → with the figure focused.

What the application is

YappyNotes is a desktop sticky-notes app for Ubuntu, Windows and macOS, written in C# on .NET 10 with Avalonia UI and SQLite. The product idea is one sentence long and the architecture follows from it: a note you open is a window on your desktop, not a row in a list. It stays where you put it, it looks the way you left it, and it is still there after a reboot.

Nothing is ever saved by pressing a button. There is no account and no sync — the whole product is one SQLite file you could copy to a USB stick, and the only thing it asks the network is whether a newer release exists. That constraint is worth holding on to while reading the rest of this page, because several decisions that look fussy in isolation are paying for it.

Four projects, and which way the arrows point

The solution has four source projects, four test projects and a shared test library. The source dependencies run one way and nothing points back:

The unusual call here is that view-models get their own project. A folder inside the app project would have been less ceremony, and it would have let an Avalonia type leak into a view-model the first time someone needed a colour or a screen bound — at which point the layer quietly stops being a layer. YappyNotes.ViewModels carries no Avalonia package reference, so that mistake is a compile error instead of a code review. The side effect is the one that pays for it daily: every view-model test runs with new, on no UI thread, in milliseconds.

Two tests keep it that way, and both were verified by breaking the rule on purpose and watching them fail: YappyNotes.Core.Tests/ArchitectureTests asserts that Core references nothing but the BCL, and YappyNotes.ViewModels.Tests/ArchitectureTests asserts that ViewModels references no Avalonia assembly and nothing beyond CommunityToolkit.Mvvm. They read Assembly.GetReferencedAssemblies(), which lists what the compiled code actually uses — the compiler drops a PackageReference nothing touches — so an unused package will not fail them and a used one will. That is the distinction worth having.

The one place a layer has to reach upward

ManagerViewModel.NewNoteCommand has to open a window, and windows live in App. IWindowManager is that seam: it is declared in ViewModels and implemented in App, so the view-model asks for a note to be shown and a test asserts against a fake that recorded the ask. IUiDispatcher, ILinkLauncher and IThemeApplier are the same pattern for the same reason.

Where the state lives

All of it is in one SQLite file, in the place each platform expects it — ~/.local/share/YappyNotes/notes.db on Linux, %APPDATA%\YappyNotes\ on Windows, ~/Library/Application Support/YappyNotes/ on macOS. UserPaths in Core resolves that in one place, and it also honours YAPPYNOTES_DATA_DIR, which is what scripts/dev-start.sh --sandbox sets. Code that builds the path from $HOME is a bug on two of the three platforms. On Linux it honours XDG_DATA_HOME, which is correct and occasionally surprising: some snap-packaged apps point that variable into their own sandbox, so YappyNotes started from a snap VS Code's terminal reads a different notes.db from one started by a desktop launcher, and the notes look as though they have vanished when they have not.

There are three tables. notes and settings arrived in migration step 1; note_timers in step 2.

notesWhy it is there
IdTEXT primary key, a UUIDv7 generated in the app
Title, Content, Colorthe note itself
X, Y, Width, Heightwhere the window is, and how big
IsAlwaysOnToppinned above other windows
IsArchivedwhat the delete button actually sets
CreatedUtc, ModifiedUtcISO-8601 text, UTC

A note's window geometry is on the note row, not in a second store. The bootstrap restores windows from it, and a note is its window; two records would drift. The cost is a guard: setting Position, Width or Height on a window raises that window's own change events, which write straight back to the note and schedule a save — so restoring a note nobody touched would rewrite every one of them on every start. NoteWindow._applyingGeometry is the guard, and it has a test that fails when it is removed.

Ids are UUIDv7 — Guid.CreateVersion7(), never Guid.NewGuid(). A v7 carries a millisecond timestamp in its high-order bits, so ORDER BY Id is creation order with no second column and no extra index, and inserts append to the right-hand edge of the B-tree instead of scattering through it. Stored as Guid.ToString() — lowercase, hyphenated, big-endian hex — which SQLite's default BINARY collation already sorts correctly. Three ways to break that are silent: a Guid.NewGuid() in a new code path, a different string format mixing two spellings into one column, and ToByteArray(), whose default overload is little-endian and byte-reverses exactly the fields the timestamp lives in.

Migrations are numbered SQL steps gated on PRAGMA user_version. Migrator runs the steps above the current number, each in a transaction that also records the new version, so an interrupted run leaves the database at a version it really is. Steps are append-only and never edited once released — an edited migration leaves every database that already ran it in a state no code path can reach, on a machine you cannot look at.

How a keystroke reaches the disk

Nothing in YappyNotes is saved by pressing a button, which means typing has to become writes, and the interesting question is how many. The answer is one per burst of typing, and the mechanism is a per-note debounce that restarts on every change rather than a timer that fires on a schedule.

Two properties of AutoSaveService are worth stating flatly, because both are load-bearing and neither is obvious from the call site.

It saves on change, never on a schedule. There is no sweep that periodically writes whatever looks dirty. That is not tidiness: the stream timer — the next section — puts a running countdown on a note, and a sweeping saver would write to disk every second forever. The decision was made in docs/plan.md before AutoSaveService was written, precisely so it would not have to be undone afterwards.

A pending write holds the caller's note, not a copy. So the write that eventually happens carries whatever the note says at that moment, rather than the state it was in when the first keystroke started the debounce. And if a window is reopened while a write is pending, Schedule replaces the stored reference — the same id may arrive as a different object, and the newer one wins.

One note, one view-model, one window

Both the manager and the desktop can open a note, and WindowManager builds a NoteViewModel once and hands the same one back — which is why IWindowManager.ShowNoteAsync takes an id. If each caller built its own, there would be two Note objects for one note, both held by the autosave, and whichever wrote last would quietly undo the other.

The timer, which never writes while it runs

A note can carry a stream timer: a countdown for back in 5:00 during a break, or a count-up for live for 2:14:33. It pauses, resumes and restarts, and it survives closing the app. It is also the most interesting thing in the codebase, because the whole feature turns on one decision: the stored timer does not change while it runs.

Five fields are persisted in note_timers, keyed on the note id, and nothing else:

note_timers
DirectionCountDown or CountUp
Durationhow long a countdown was set for
Labelwhat it is for — "Back in", "Live for"
StartedAtUtcwhen the current running stretch began; null means not running
Accumulatedtime banked from stretches that have already been paused

The number on screen is a pure function of those and now: 

running   remaining = Duration - (Accumulated + (now - StartedAtUtc))
paused    remaining = Duration -  Accumulated

Start sets StartedAtUtc. Pause banks the stretch that has been running into Accumulated and clears StartedAtUtc. Restart zeroes Accumulated and starts again; Reset zeroes both and stops. Finished is not stored at all — it is remaining <= 0, asked whenever anyone looks. Those four methods are the complete list of things that change a stored field while the timer is running. The label, the length and the direction are settable too — but only while it is stopped, which is what NoteTimerViewModel.CanEdit enforces, and each of those setters writes only when the value actually changed.

Three things fall out of that design, and each one is a problem the app then does not have.

Ticking never causes a write. Not because a rule says so, but because there is nothing to write: no persisted field differs between one second and the next. A design that stored "seconds remaining" would have handed AutoSaveService a note that is dirty every second forever, and the fix at that point is a special case threaded through the save path.

It is testable without sleeping. FakeTimeProvider advances two hours in a microsecond, so every timing test is exact and none of them is flaky on a loaded machine. This is the same TimeProvider already threaded through Note.Create and NoteService, so it cost nothing new.

And it survives a restart for free — which is the next figure.

The property that cannot be tested by counting writes

"Ticking writes nothing" looks like it should be a test that runs a timer for an hour and asserts zero writes. It is not, and the first version of that test passed against the bug it was written for: a one-second tick keeps resetting a 750 ms debounce, so a ticker that did ask for a save would still never produce one. NoteTimerViewModelTests.Ticking_ForAnHour_NeverAsksForAWrite asserts against the transition callback instead — the thing the view-model calls to schedule a save — rather than against the disk.

The display has to tick even though nothing changes, and that is where the timer touches the layer rules. NoteTimerViewModel drives it with TimeProvider.CreateTimer, which is BCL and therefore allowed in YappyNotes.ViewModels — a DispatcherTimer would have been an Avalonia type and would have failed ArchitectureTests. Its callback arrives on a thread-pool thread, and an Avalonia binding must be updated on the UI thread, so the hop back goes through IUiDispatcher, a seam declared in ViewModels and implemented in App. Autosave completing off-thread needed the same seam first; the timer was its second caller.

The ticker also only runs while the timer does, and stops again the moment a countdown finishes: the display reads 0:00 and cannot change, so waking up once a second to redraw it is work nobody asked for.

Two smaller decisions are worth knowing because both came from using the thing. A finished countdown reads 0:00 and turns red rather than counting past zero — it showed the overrun as "-2:05" at first, which reads as a fault. RemainingAt still goes negative, because HasFinishedAt needs the sign; the clamp lives in DisplayAt alone, and the colour is what distinguishes a finished timer from one that has not started. And the timer's settings are locked while it is running — CanEdit is !IsRunning, and it disables the … button that opens them. Moving the finish line halfway through a countdown is a way to be confused. The settings live in a flyout rather than on the bar because a note is 280 px wide by default and a label, a direction, presets, minutes and seconds do not fit beside a count; they were clipped to unreadable stumps when they tried. Setting a length also clears what has already run — "10 minutes" means a ten-minute break, not ten minutes minus what you used.

The trap the timer introduced

Note.Timer is the first reference-typed member on Note, and Note.Copy() is what makes a repository round-trip by value. Copy was trivially correct while every field was a scalar; the moment a reference landed it had to deep-copy, or two notes would share one timer and pausing a countdown in a window would pause it in the database too. NoteTimer.Copy() is that deep copy. The two contract tests that guard round-tripping by value would have kept passing while it was broken, which is why the contract got a timer case in the same commit as the field.

One contract, answered twice

INoteRepository exists in Core not because a second store is expected to ship, but because the in-memory fake is what makes the service and view-model tests run in milliseconds with no file on disk. That is the seam earning its keep on day one. The risk it brings is the usual one: a fake that behaves differently from the real store is worse than no fake at all, because it makes tests pass for reasons that will not hold in the app.

Two of the contract's cases exist only to keep the fake honest: the store round-trips by value, so mutating a note you inserted — or one you were handed back — must change nothing. SQLite gets that for free because it serialises; an in-memory dictionary does not, and would otherwise hand out live references that let a test mutate the store by accident. That is also the reason Note.Copy() exists, and the reason the timer's arrival made it dangerous.

The service above draws the line the other way. A repository stores what it is given and never filters archived notes out; NoteService is where "which notes should a reader see" and "delete means archive" live, and nothing above it holds an INoteRepository of its own. PurgeAsync refuses a note that is not archived, which is the second half of that rule: the only path to a real delete goes through the archive, so no single action destroys a note a reader can still see on their desktop.

Reading the source

In the order that makes the rest legible:

  • src/YappyNotes.Core/Note.cs and NoteTimer.cs — the whole domain, and the two files where the reasoning above is written down as XML doc comments.
  • src/YappyNotes.Core/INoteRepository.cs, then tests/YappyNotes.TestKit/NoteRepositoryContract.cs — the interface and its definition.
  • src/YappyNotes.Core/NoteService.cs and AutoSaveService.cs — the policy.
  • src/YappyNotes.Data/Migrator.cs — the schema, as the two SQL steps that made it.
  • src/YappyNotes.ViewModels/NoteViewModel.cs and NoteTimerViewModel.cs — everything the window binds to.
  • src/YappyNotes.App/AppServices.cs — the composition root, and the only C# file in YappyNotes.App that names YappyNotes.Data at all — the project reference itself lives in the .csproj, as it must.

The project is test-driven, and LOOP.md is the rule set rather than an aspiration: no production code without a failing test that needed it, a bug starts as a test that reproduces it, refactor only on green, and never commit a red suite. Test names are Subject_Situation_ExpectedOutcome, three parts always; an "and" in the middle part means it is two tests.

The suite is xunit v3 in every test project, and that uniformity is deliberate rather than tidy. Avalonia.Headless.XUnit 12.x is built against xunit.v3.extensibility.core; under a v2 runner its [AvaloniaFact] attribute is not discovered at all, so the project reports no tests and the run still passes. Nothing goes red when that happens, which is exactly why it is worth knowing about. 

dotnet build yappynotes.sln
dotnet test  yappynotes.sln
dotnet format yappynotes.sln

dotnet watch test --project tests/YappyNotes.Core.Tests   # the fast ones
scripts/dev-start.sh --sandbox                            # a throwaway database

Use --sandbox before touching the schema. Testing a migration against your own week-old notes is how notes get lost.

What is deliberately not here

Milestone 6 is two things rather than the nine it used to be: a tray icon and rich text, and both are in. The rich-text argument is the one worth reading, because it is a storage decision wearing a rendering costume — Markdown kept in Content means no migration (Content is already TEXT), LIKE search keeps working, export stays nearly free, and the file stays readable in a SQL browser. A rich-text blob would break search and need either FTS or a second stored plain-text column.

Everything else is parked with its reason attached, so that none of it is rediscovered as an oversight. Sync is rejected rather than deferred: "no account and no sync" is a product goal, and it is what lets the whole application be one file. Images, reminders, tags, stacking and a global hotkey each have their own paragraph in the plan; the hotkey's is the most interesting, because it is genuinely useful and genuinely unreliable — X11, Wayland, Win32 and macOS each register one differently, and Wayland mostly refuses without a desktop portal.

Links came before rich text, and were offered beside the note while the body was only an editable TextBox. Now the note is drawn formatted, a link — bare, found by LinkScanner, or labelled Markdown — is clickable where it is written, and the bar beside the note is left for while you are editing the Markdown and cannot click one.

The part of that feature worth getting right is not the rendering but the launching. TopLevel.Launcher.LaunchUriAsync hands a string to the OS shell; note content is text a reader can paste from anywhere, and a notes.db can be copied between machines. So the scheme is allow-listed — http, https, mailto, and nothing else — and anything unrecognised renders as ordinary text. file: is refused by name because it will open anything on disk, and unknown schemes are refused as a class because custom protocol handlers are registered by whatever else is installed. The check is made twice on purpose: once in LinkScanner when the link is found, and again in AvaloniaLinkLauncher, which is the one line where a string out of a note reaches the shell. That duplication is not something to tidy away.
